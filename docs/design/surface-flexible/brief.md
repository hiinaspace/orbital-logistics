## Lean and alternatives
Lean: new separately versioned surface-flexible domain, one reusable single-ship launch/descent pair authored offline in a primary-only local operation model, plus the existing live coupled station service machinery outside the surface sphere. An interface is a boundary state, not a new berth/station/teleport destination. Ship remains one identity/tank/cargo throughout. Ground initial state and pad occupancy are actual surface corotation; orbital legs start from the contract's exact exit and target its exact entry, not drawing interpolation.

Critical simplification under consideration: fixed acceleration steering law + high enough engine force ceiling makes local path independent of instantaneous wet mass; rocket-equation fuel/force use actual mass. Cache canonical nominal path once, rotate/shift at admitted pad phase; each use gets exact start/end states and actual fuel consumption. Do not reintegrate every detailed near-surface point or run an online launch solver. Local contract ignores distant Mote (explicit primary-only model); live orbital legs and station keep full field. Quantify its approximation, avoid claiming all phases are the same force model. Prefer this to a dense grid interpolating loadouts without evidence, or rerunning two detail-heavy global solvers every launch.

Outbound orbital departure time determines ground launch epoch=departure-ascent duration; exact corotating pad phase fixes exit orientation. Return orbital endpoint targets descent entry rotated from future landing-pad phase. Flexible outbound windows and relay dwell choose phases instead of a hard wall-clock launch cadence. Cache geometry; keep budget/fuel/current-state preconditions strict. At the station, loaded maintenance uses the actual visitor fuel (larger funded tank may be needed); after top-up the return template must budget the actual reduced mass. Ground refuel and station fuel top-up count once in existing shared ledger.

Architecture fork: small new mission/trip facade composing surface contracts and existing coupled ownership/planner, with parameterized physical boundary providers and schedule validation, vs significant independent clone of adaptive engine/world/view. Prefer a bounded opt-in extension with old-domain exact regression evidence. Do not mutate old validators to silently accept unsupported physical fields or add a generic graph/logistics engine.

Display: same single Tern timeline, ground launch/land events, paid fuel curves, surface port and close zoom. Dense nominal surface geometry should be immutable reusable data; transmitted per-visit descriptors must be bounded and not resend huge detail arrays. Held cursors/rewind retain known-at admission and brackets. Force/attitude display must respect surface vs orbital propulsion modes; no free endpoint velocity or fuel reset. Ground transport only if numerical landing fails, visibly labeled separate operation, not disguised physics.
