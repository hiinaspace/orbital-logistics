## Mostly worked proposal and open decisions

1. **One canonical 6-component engine, boundary conversion.** Lean [x,y,z,vx,vy,vz] under new schema/model version. Explicit loader upgrade accepts v1 fixtures and turns zero-z states/rails into canonical data; durable original fixtures and baseline evidence retained. Avoid parallel 2D and 3D propagators and hidden four/six indexing unions. Existing tests/source consumers migrate coherently; compatibility witnesses compare legacy behavior. Snapshot anchors are disposable: reject old snapshot or replay explicitly, never relabel old state. Is a strict version bump sufficient, and what is the smallest clean input/runtime type seam? Rejected: six coordinates with velocity still at2,3 for compatibility (confusing long-term); dynamic dimension physics (too many latent assumptions).

2. **Oriented analytic rails.** Lean explicit orthonormal right-handed plane basis u,v plus 3D center for circular rails, strict unit/perpendicular validation, versioned normalization at input. Legacy u=(1,0,0),v=(0,1,0). Body ephemerides still externally prescribed circles/fixed positions; no hierarchy/framework needed initially. Need consistency for port constraints and source speed in safety proof. Alternative normal+reference-axis chosen automatically introduces pole discontinuities. Can a smaller explicit representation serve future binary/inclined systems without framework debt?

3. **Spatial burns with preserved planar semantics.** Lean retain legacy burn variant restricted to legacy XY-coplanar domain, plus versioned explicit-plane radial/transverse/normal variant with a supplied orientation normal. Compute R from relative position, T=normalize(N_ref cross R), N=R cross T; reject degenerate geometry rather than invent axis. Normal delta-v is paid. Alternative inertial Cartesian impulse variant useful for offline solvers but may be excessive if plane variant can encode their results. RTN from instantaneous angular momentum differs from old CCW convention on clockwise trajectories; must not silently redefine old burns. Which representation best balances simple authoring, robust offline transfer solving and migration? This overlaps rail plane definitions and planar solver guard; merge as appropriate.

4. **Keep targeting narrow; generalize diagnostics only where sound.** Lean leave legacy two-variable solver explicitly XY-planar, reject out-of-plane target/reference/source/burn inputs; upgrade closest-approach/apsis dot products to 3D. Do not advertise a general spatial solver. Runtime execution supports spatial burns regardless of solver limits. A lunar freight experiment may use offline independent shooting in a bounded planar binary and emit explicit paid engine programs, not general runtime dispatch. Is separating solver domain from engine dimension clean enough? Need no new human UX decision.

5. **Spatial frames, planar presentation.** Lean full 6-state translation and orientation transform with velocity term; generic axis/unit basis if small, preserve existing Z rotating set metadata by explicit upgrade. Renderer projects XY only, no depth sorting/perspective camera. Add inclined physics fixture and test transform covariance rather than imply current viewer can inspect all3D geometry. Is arbitrary rotating axis needed now or a versioned Z-only frame sufficient with a clear seam?

6. **Numerical/compatibility gate before freight.** Plan baseline old program/ledger snapshots; zero-z planar parity and independent oracle; inclined Kepler orbit, moving inclined binary source, out-of-plane burn and fuel, genuinely 3D collision/capture rejection, frame position+velocity tests, canonical partition/snapshot invariance, h/h2/h4 against independent DOP853. Keep node/work bounds; select shorter validation horizons to fit refinement budgets. Browser old viewer regressions. Do not change integrator or claim long-horizon general accuracy. Where is the largest missing proof/likely failure? Specify tolerances tied to capture or fixture scale and checks that catch indexing errors.

7. **Lunar freight feasibility after gate.** Current circular fixed-primary ports cannot represent a lunar/DRO station physically. Lean bounded experiment before production schema: solve a paid transfer to an integrated target trajectory in binary gravity, independent tight oracle + step convergence, explicit target state ephemeris from canonical dynamics (not display interpolation). Only extend docks to trajectory-backed station if arrival position/velocity and constrained dwell/undock semantics can be represented honestly; otherwise show valid free-flight rendezvous traffic without dock/service fabrication, or report feasibility result and stop. Alternative a smaller inclined fixed-primary freight set can exercise3D without inventing lunar ports, but should not dodge the user's lunar request without attempting. What smallest architecture seam makes a meaningful set feasible without a new general ephemeris/scheduler platform? This is optional work, bounded by uncertainty; rank relative to foundation.

8. **Labels.** Lean fixed remembered anchor per object with collision fade/hysteresis and selected/hover priority, predictable reset on scene change. Avoid per-frame first-fit relocation. Presentation state independent physics. Synchronized views can wait; don't spend design effort here in this review unless correctness couples it to3D.
