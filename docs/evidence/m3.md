## Try the scene

Refresh `http://127.0.0.1:4178/`, choose **Delivery**. Its initial program loads
0.200 cargo at Home, flies to Depot, unloads and refuels, but stays there; the goal
therefore reads **Return to Home**. **Example round trip** adds the authored return
program to the draft as one undoable change. It does not execute or search for a
route. **Execute plan** runs the shared core; 16× shows the complete trip quickly.

Port operations have their own editable queue. Click an operation to preview its
epoch and change its port, time or action; `+` adds one. Transfer cargo is signed
(+ loads the tug, − unloads); refueling is a specified positive quantity. Save,
delete, undo/redo, synchronized Home/Depot frames and JSON reload are supported.
Inventories follow preview time, including service completion boundaries. The
panel shows the quota, empty return, required fuel reserve, completion time,
propellant consumed and fixed one-tug hardware cost. It adds no charter commentary
to the game UI.

## Physical/discrete contract

The two ports are explicitly **kinematic, infinite-inertia scenario fixtures** on
circular rails about one fixed primary. They have finite cargo/fuel stocks and
capacities. Their angular rates agree with μ and radius. A docked tug follows its
port's rail; flight still uses the same integrated dynamics as every prior scene.
This does not validate free-flight station assemblies or stationkeeping costs.
The additional discrete contract is versioned `kinematic-ports-v1`; existing
M0/M1/M2 bundles retain their unchanged propagation model and optional-free shape.

- Docking checks both distance and speed (1e-5 each). It rejects a missing arrival
  burn rather than supplying a large capture adjustment. The remaining bounded
  velocity impulse is fully charged using current dry/cargo/wet mass. Position
  attachment within the radius is the explicit small interface approximation.
- Loading/unloading/refueling requires docking at the named port. It checks source
  stocks, ship/port capacities and finite mass before starting. Resources remain
  unchanged during service; completion atomically commits the whole exchange.
  The tug/port remains occupied during service, and another operation or early
  undock fails rather than cancelling/reserving a successful-looking continuation.
- Canonical boundaries include authored operation epochs and service completions.
  Simultaneous order is completion → undock → burn → dock → transfer start;
  surface termination still takes precedence. Dock/undock adds no free departure
  impulse. Burns use the cargo mass after completed transfers.
- Failed actions stop prediction and block plan acceptance. Discrete state,
  pending service, event cursors, inventories and resource ledgers are included in
  canonical nodes and replay-validated snapshots. Warp/scrub do not change events.
- Delivery credit is the destination's **net inventory increase**, preventing
  reload/unload from counting the same cargo repeatedly. Completion also requires
  docking at Home, an empty tug and fuel ≥0.150, with no unfinished service and a
  valid full program. Refueling does not reduce the score's consumed propellant.

## Verification and retained artifacts

Build/typecheck, **60 simulation tests**, **17 production Chrome browser tests**,
Ruff format/lint and ty pass. No browser page/console errors. Added tests cover
resource conservation, dynamic burn mass, service timing, simultaneous order,
finite stocks/capacities, duplicate/early transfers, failed capture and residual
fuel rejection, return/fuel requirements, no credit from a failed future action,
warp/query partitioning, mid-service snapshot replay, undo and browser repair.

`npm run evidence:m3` runs five cases at h=1/512, 1/1024 and 1/2048: round trip,
missed docking, early undock, empty source and a capture interface tightened to
1e-8. Independent SciPy DOP853 replay implements the discrete ledger separately,
using independently calculated impulse axes/fuel, analytic port states and dense
flight propagation. All cases agree on terminal status/epoch, operation trace,
cargo and stocks; fuel disagreement is <1e-11. Maximum sampled position error is
1.46e-12 and velocity error 7.77e-13. The independent oracle's own tightening
changes sampled states by <9.22e-12. The tightened-capture trip still succeeds.
These are fixture/sample measurements, not a universal close-approach bound.

Chrome/Node trajectory and fuel comparisons allow 1e-12 for runtime trigonometry;
discrete event times/order and stocks remain exact. Save/reload checks are exact
within the same runtime. Portable authored programs remain the durable source;
snapshots are validated replay accelerators, not a cross-runtime bitwise promise.

`node scripts/m3-browser-evidence.mjs` records a separate headless browser against
the production preview: perturb docking, observe failure, repair it, execute the
round trip and save the actual browser replay. Two individual application
input-to-fresh-paint observations were 77.3 ms (failed edit) and 168.3 ms (repaired
full path), alongside regression-test load. They are not a latency distribution;
the full 24-unit M3 path is above the provisional ~100 ms target in the latter run.
