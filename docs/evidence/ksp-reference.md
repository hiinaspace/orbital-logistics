# KSP maneuver-editor references

Date: 2026-10-06. Bounded desk research from the official KSPedia manual and mod maintainers' documentation/source. Neither KSP nor its mods were installed or run for this task; screenshots and behavior below are documented references, not firsthand UX observations. The useful comparison is the authoring surface: KSP uses patched-conic orbit segments, whereas Orbital Logistics intends prescribed moving gravity sources and direct ship propagation. Do not copy KSP's solver or imply the models are equivalent.

## Documented behavior vs design inference

| Status | Reference finding | Orbital Logistics implication |
|---|---|---|
| Documented in official KSPedia | A node is created at a chosen point on an existing or future path. Its gizmo has six signed maneuver directions. Map-view path styles distinguish current/future orbit patches and nodes; target orbit aids show where the active vessel and target are at the same time at a closest approach. | Treat time and Δv as two editable parts of one authored maneuver. Keep forecast branches visually distinct and make predicted encounter location/time legible without requiring the player to read an orbit table. KSP's patch colors and SOI transitions are tied to patched conics and shouldn't be copied literally. |
| Documented in editor mod sources | PreciseNode exposes editable maneuver time and prograde/radial/normal values, resulting Δv, and ejection angle; button clicks and keypad shortcuts change signed components and time, with an adjustable increment. Precise Maneuver layers optional pager, presets, fine `+/-` input, orbit tools, a stock-like gizmo, next-encounter focus/distance, orbit data, and patched-conic display controls. | Keep the path/gizmo as the primary spatial edit; make numerical correction, explicit increments, and maneuver selection available alongside it. Treat next encounter and its closest-point distance as diagnostics for a selected encounter branch, not an autonomous route choice. |
| Documented in MechJeb source | The node editor names snap targets (periapsis, apoapsis, target-relative AN/DN, equatorial AN/DN), exposes component values, time shift, tolerance, and patched-conic display mode. A separate planner can create a new node or replace the last and can compute named operations. | An apsis snap is a useful small M1 convenience. Keep automatic operations/targeting beyond M1. Expose event identity and selected body; don't let changing the display frame silently choose another physical burn direction. |
| Inferred design pattern | A continuous visual manipulation can coexist with a precise panel offering smaller signed increments, exact time/component entry, and a way to select/focus/delete one maneuver. This gives a workable visual-first-to-numeric-on-demand progression. | Start with the path and handle. Reveal epoch, signed components, total Δv, and cost when the player selects/expands a node; provide explicit fine/coarse step control for small corrections. Preserve undo/clear and baseline-vs-edited path. These are recommendations, not claims that KSP's UI is subtle or easy to learn. |
| Not established by these sources | Whether stock KSP's camera orientation affects the drawn gizmo's screen orientation, exact screen-space snapping/drag semantics, sensitivity curve, continuous hover-to-time behavior, how competing future closest approaches are selected, or how often the encounter markers jump between branches. | Inspecting the actual UI would be needed before borrowing its interaction feel. In our model, label the maneuver basis in a chosen inertial/local orbital frame and make camera motion presentation-only; test this invariant directly. |

## Narrow reference set

- **Stock KSP map/node concepts — official KSPedia (console editions).** The official [Xbox KSPedia](https://static-files.kerbalspaceprogram.com/pd/KSPedia-XB1.pdf) and [PlayStation KSPedia](https://static-files.kerbalspaceprogram.com/pd/KSPedia-PS4.pdf) describe adding a node on the current/future path, adjusting with six handles, and distinguish orbit patches, node markers, and closest-approach markers. The manual is useful for the semantic shape of the tool, not desktop mouse bindings; it is a console manual. The game screen is presented in screenshots there, but visual details should be checked in-game before borrowing them.
- **PreciseNode.** Its maintainer's [README](https://github.com/linuxgurugamer/ksp-precisenode/blob/master/README.md) documents the value/time widget, final Δv/ejection-angle readouts, adjustable increment, signed keypad controls, and left-click/right-click plus/minus behavior. This is a direct source for fine/coarse input and numbers-on-demand. It does not document a closest-approach chooser.
- **Precise Maneuver (PM).** The [maintainer's README](https://github.com/zer0Kerbal/PreciseManeuver) describes optional modules: maneuver pager, presets, precise +/- input, orbit tools, gizmo, next encounter/closest-point distance, orbit info, and patch display. Its [maintainer screenshots](https://zer0kerbal.github.io/PreciseManeuver/Marketing) show the modules and their panel arrangement. The latest explicit release listed in the [changelog](https://github.com/zer0Kerbal/PreciseManeuver/blob/master/changelog.md) is a Jan 2023 KSP 1.12.4 prerelease; current game compatibility is unverified here. **Maneuver Node Evolved** is a related DMagic project, but its [latest listed release](https://github.com/DMagic1/KSP_Better_Maneuvering/releases) was v5.0 for KSP 1.8 in 2019, so I treat it as historical rather than a current-maintenance reference.
- **MechJeb node editor/planner.** Its [current source for the node editor](https://github.com/MuMech/MechJeb2/blob/dev/MechJeb2/MechJebModuleNodeEditor.cs) and [localized labels](https://github.com/MuMech/MechJeb2/blob/dev/Localization/en-us.cfg) document event snaps, component inputs, time shifting, tolerance, conics mode, and node merge. The project's [repository](https://github.com/MuMech/MechJeb2) remains actively developed, but its planner is an automation/operation layer as well as an editor; use it for useful field and snap concepts, not the first-milestone interaction contract.
- **Transfer window selection.** Alex Moon's [Launch Window Planner](https://alexmoon.github.io/ksp/) lets the user click a point on a transfer plot to inspect that transfer's details; TriggerAu's [in-game Transfer Window Planner](https://github.com/TriggerAu/TransferWindowPlanner) implements the planner in KSP. This is a later departure-phase selection pattern: compare candidate windows, then select one to seed an authored departure. It is separate from choosing a burn epoch along one ship's current forecast and should not pull launch-window optimization into M1.

## Recommended adaptation

For M1, mirror the astrogation editor prefix rather than KSP's full flight-planning stack: select a ship; make its forecast visually distinct; hover to inspect future state and click to pin an epoch; set one impulse with in-plane local components; show the resulting branch against baseline; make one named apsis snap, undo, exact values, and coarse/fine increments discoverable on demand. Keep camera frame choice separate from maneuver-basis meaning. KSP documents radial/prograde/normal axes, but the selected references do not settle how their on-screen handles respond to camera orientation; the game's installed tutorial gives an explicit further warning to inspect gesture semantics rather than assuming conventional press-and-drag.

The KSP tutorial concepts around encounter markers, node snapping to target events, phasing, and rendezvous selection can inform M2 assistance. A transfer-window plot can later inform the mission-level choice of departure phase, but remains distinct from a manual node editor and the full prescribed-force simulator. No KSP mod's patched-conic predictions should be accepted as validation of Orbital Logistics encounter physics.
